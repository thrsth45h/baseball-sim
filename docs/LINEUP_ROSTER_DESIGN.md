## 利用者に届く成果と限界

次のAPKでは、**操作球団の打者12人から出場9人と打順を決め、試合を進め、その選手に成績が残ること**を目標にする。控えと交換し、次の試合で使い、アプリ再起動・save/load後も同じ出場者と記録を保つ。coreだけの実装で完成とはしない。

12人（出場9人＋控え3人）はこの接続試作の固定データであり、一軍・二軍・ベンチ入りの製品規約ではない。144人に増えるが、年齢・能力・守備位置・架空の公式打率等は埋めない。既存P01〜P09のIDは人物を識別する値として維持し、P10〜P12を追加する。末尾の数字は打順・背番号ではない。

**全員同じ仮確率を保つため、入替えや打順変更で勝ちやすさの差はまだ生まれない。** 同じseedなら打順枠の逐球結果・得点・勝敗は同じで、出場者と個人成績の帰属が変わる。編成操作と試合・記録・保存の接続を検証する成果で、戦力差を考えて遊べる段階B全体の完成とは呼ばない。

## 現状の問題と根拠

- [Schedule.kt](../android/core/src/main/kotlin/com/example/baseballsim/season/Schedule.kt)のPlayerは固定slotを持ち、各球団9人だけを生成する。
- [Records.kt](../android/core/src/main/kotlin/com/example/baseballsim/season/Records.kt)は固定順で個人へ投影し、シーズン合計でも同じslotを要求する。画面の並びだけ変えても出場者は変わらず、現在の並びで過去を投影し直すと成績を付け替える。
- [GameSession.kt](../android/core/src/main/kotlin/com/example/baseballsim/core/GameSession.kt)の記録は両軍9打順の18枠。試合内で交代しない条件なら、この1球エンジンを再利用できる。
- [Season.kt](../android/core/src/main/kotlin/com/example/baseballsim/season/Season.kt)は日程とseedの計画から直接開始し、[Checkpoint.kt](../android/core/src/main/kotlin/com/example/baseballsim/season/Checkpoint.kt)に出場者入力がない。復旧にも同じ打順表を含める必要がある。
- [CheckpointCodec.kt](../android/core/src/main/kotlin/com/example/baseballsim/season/CheckpointCodec.kt)はv1・108人を厳密に要求する。既存15ファイル不変のUI変更では済まず、今回はseason/codec/storeの限定拡張が必要になる。

[Pennant Spiritsの起用法](https://pennantspirits.ifdef.jp/manual_9.html)は打順・投手配置・昇降格等を分け、[試合画面](https://pennantspirits.ifdef.jp/manual_g_8.html)では開始前にオーダーを確定する。本作でも未来の起用設定と、その試合で確定した出場者を区別する。ただし参照作品の登録人数、先発人数、左右/DH別オーダー、CPU方針を今回まとめて採用しない。参照はマニュアル本文であり、内部実装の検証ではない。

## 人物・未来の設定・試合入力を分ける

1. **人物**はplayerIdと所属球団。打順は人物の不変属性にしない。今回は所属固定で、移籍の履歴モデルは作らない。
2. **球団の次戦用オーダー**は9人の順序。変更しても日程、割当済みgame seed、過去の結果は変えない。日程計画と出場者の確定は別の値とする。
3. **試合開始入力**はGameIdに結び付いた両軍各9人の不変スナップショット。試合開始時に、その時点の保存済みオーダーから作り、最初のadvanceより前に既存の原子的保存境界で確定する。未保存の候補をUIへ公開しない。
4. **進行中checkpoint・完了summary**はその試合開始入力を保持する。復旧・直近試合の再生・結果検証は現在の球団設定ではなく、その入力を使う。core内のaway/homeの打順枠は、その試合の対応表で個人へ結ぶ。
5. **当季の合計**はplayerIdで全完了試合の貢献を加算する。現在の打順を合計値のslotとして保存しない。試合別の打順は各試合の事実として残し、同じ選手が次戦で9番になっても累積先は同じ。

ロスターとprojectionは世界の形式へ結び付ける。v2の144人をグローバルな既定値へ差し替えて旧v1の固定9人/108人まで変えない。旧factory・旧形式の検証は旧ロスターを使い、新形式の生成/描画は明示した新ロスターを使う。一覧/集計もv1は108人、v2は144人とする。

ロスターの検証元は対応versionの固定fixtureである。保存bodyにロスターを含める場合も、その固定ID/所属/順序と一致を検査する。保存body内でロスターと打順を同時に書き換えれば未知IDを受理できる仕組みにはしない。任意の選手生成/ロスター編集は今回の機能ではない。

日程・seedは従来のcanonical planと照合し、出場者は保存された試合開始入力と所属/一意性を照合する。現在のオーダーと過去の出場者が一致することを要求しない。一方、保存された入力の重複・球団不一致・人数不正を受理しない。coreへ投手IDや能力入力が追加されたと見せかけない。

## 画面と確定操作

新形式のホームに「打順・出場選手」を追加する。画面には現在の9打順と控え3人を表示し、打順の上下交換、控えを選んで特定打順の選手と交換できるようにする。控え表示順は固定ロスター順で、現在の出場者を除いた順序とする。ドラッグ操作を必須にしない。

編集途中はUI内のドラフトで、適用前に試合へ影響しない。「適用」で9人の完全なリストを一度だけ保存し、「戻る」や取消はドラフトを破棄する。変更なしの適用は無効。回転はドラフトと結び付いた元tokenを復元できるが、復元を自動適用しない。世代や公開revisionが変われば古いドラフトを破棄して最新値へ戻す。新しい通常画面の閲覧・球団切替・戻るだけでread/execute/save/replayを増やさない。

新しい編成確定commandは、ドラフト開始時のworld/generation/revisionを期待tokenとして持つ。UI受付だけでなく、Coordinator/Storeの実際の更新境界でも一致を要求する。別の保存/SELECT/進行/load等が先に確定していれば、古い編集を自動で現在の世界へ当て直さず拒否し、最新状態を明示的に確認できるようにする。これは**新しい編成commandだけ**の契約で、既存新規/load確認が未公開DB変更まで検出できるという主張へ広げない。

編成・進行位置・operation receipt・保存frame/hashは既存のCAS/transactionの検査へ含める。検査されないsidecarや、確定後に別保存するUI設定で編成を持たない。失敗時は未保存候補を破棄し、同じoperationの再受付で二重保存や試合開始を起こさない。編成の適用自体はRNGやadvanceを消費しない。

選手一覧/詳細は144人を表示できるprojectionへ拡張する。新形式では「固定打順」を人物属性として出さず、現在の「n番」または「控え」と、確定試合の5件数を示す。試合画面は現在打者の実選手IDを試合開始入力から示す。詳細や記録から、その球団の現在設定で過去の出場を推測しない。

## 保存・旧形式・復旧

推奨は**同じRoom schema1の保存境界を使い、payload/試作用versionを明確に分けてv1/v2を扱う方式**。新形式にはロスター、各球団オーダー、進行中/完了試合の開始入力と144人の集計を含める。`season-roster-v2` と `pennant-season-checkpoint-v2` 等の別識別子を使い、対応するsummary/gameの形式も明示する。受理するversionの組合せを列挙し、未知versionや一つの世界/payload内部の不整合なv1/v2混在、不正な余剰byteは拒否する。working世界とmanual slotが別の形式で同じDBに存在することは正当であり、拒否しない。v1の人数制限を無条件に緩めない。

- 既存v1世界はv1の9人/108人のまま読み、進行・保存・復旧・閲覧できる。編成編集は提供しない。新形式を試すには既存の置換確認を経て新規開始する。既存世界を自動変換しない。
- 新規開始はv2を既定とする。旧単独1試合モードと旧coreの参照は保持する。v1参照テストの初期化まで暗黙にv2へ切り替えない。
- 新規開始で旧manual slotを消さない。slotは元のpayload形式を保持し、v1 slotをv2世界へ、v2 slotをv1世界へloadしても形式を保ち、従来どおり新generationでUI/ドラフトをリセットする。試合中の手動save/load不可は維持する。
- 起動の読込失敗、未知/壊れた保存を新規世界へ置き換えず保持する。DB削除・再作成・破壊的migrationを使わない。既存CAS/receipt/台帳/再生/hash検査を省かない。
- 旧APKがv2を読めるという後方互換や、今回のschema1を製品DBとして永久維持する約束はしない。SQL schemaの変更や既存v1の自動変換が必要と判明したら、実装で独断採用せず設計へ戻す。

この追加はD061の試作保存判断として承認された。D056の製品DB・長期履歴/移行をCONFIRMEDにしない。旧形式を廃止する案より安全だが、両形式の試験とコード分岐が増える負担がある。

## 既存の性能比較の適用範囲

旧[性能比較生成器](../android/tools/generate_store_benchmark.py)は12個の共有依存ソースが旧固定commitと同一であることを要求する。season/codec等を拡張する本工程では、この比較前提が成立しなくなる。固定hashを書き換えて「依存不変」の比較を続けたとは扱わない。

承認後のCI変更として、この旧比較は前提検査の結果を `not_applicable`（変更された依存のpath/hash・理由・source付き）で残し、本工程の性能採用ゲートから外す。性能比較の未実施は成功/改善率に数えない。凍結baseline/Git objectの破損・欠落等の実エラーを握り潰す処理にはしない。旧比較の定義、元source/raw、PR #46/#49の結果は履歴として保持し、新しい性能比較の前提/基準の設定は別工程とする。

旧generated baselineは既存のschema1 fixture/保存検査でも使われる。必要な互換adapterは変更内容と依存の出所を明示し、現在の共有helperを使ったものを旧APK実行や旧ABBAと同一視しない。既存のv1保存・故障・競合・receipt・改ざん拒否等の正しさのassertは維持し、以前に凍結したv1 frame/記録済みDB/操作結果も独立期待値として使う。両側が同じ新helperを使う差分試験だけで互換性を証明しない。

## 代替案・反証

| 案 | 利点 | 問題・判断 |
|---|---|---|
| 推奨：打者12人/試合間の打順と入替え | 操作→出場→個人記録→保存をAPKで通し、人物と打順の誤帰属を先に除く。既存1球coreを再利用できる | 戦力差はまだなく、保存拡張の作業もある。段階B全部の完成ではない |
| 画面だけ並べ替える | 作業が少ない | 実際の出場や記録へ反映されず、編成機能と呼べないため不採用を推奨 |
| 投手配置/途中交代/疲労/能力差まで一度に扱う | 戦略として遊べる成果へ近い | 投手ID・途中交代のイベント帰属・守備/走塁/記録・未較正係数等が加わる。別の重要判断を多数抱えるので今回の最初の範囲にはしない |
| 旧保存を捨て新DBだけ作る | v1分岐を避けやすい | 旧セーブの利用を失う。ユーザー端末のデータを自動削除する根拠にはできない |
| 旧v1を自動で144人へ変換する | 一つの形式へ統一できる | 過去のID/slotと新しい意味の変換、slot/進行中復旧の証明が別途必要。今回は旧形式のまま維持する方を推奨 |

次に投手/途中交代を扱う際は、今回の開始時打順の対応表だけでは不足する。登板/交代の時点と出場者の事実を記録する契約を別に設計する。その後、能力効果とCPU判断を加えて段階Bの「編成してシーズンを遊ぶ」を評価する。段階B〜Dの一括実装承認は求めない。

## 受入条件

1. 新形式12球団×12人の一意な144 IDと9出場/3控えを一覧・詳細・編成から確認。初期値、打順交換、控えとの交換、取消、回転、適用連打、他球団閲覧を検査する。A球団を編集後にSELECTでBへ移っても、Aの保存済みオーダーが次戦で使われる。
2. 試合1でP01が1番、試合2で9番でもP01へ累積する。P10を次戦へ入れてもP01の以前の件数が移らず、未出場者は0件。集計は保存結果から独立再計算し、全144人の5件数と一致する。
3. 適用前ドラフト/閲覧往復で追加Actions・DB更新0。適用1回では編成以外の得点/日程/seed/RNG/advance/既存結果が不変。適用取消・古いtoken・二重受付・故障/競合時も未確定値を公開しない。
4. 開始時に両軍の出場者を保存し、次戦用設定を後で変えても過去summaryと既存checkpoint全値は不変。途中の出場者改変、不正所属/重複/不足/slot不整合や未知versionを拒否し、DBを修復・消去しない。
5. 同seed・同じ試合境界での同じ編成操作列なら、1球/1打席/試合終了/日程skipで全出場者・逐球状態・RNG・得点・完了個人記録が一致する。seedだけで同じ選手起用まで決まるとは表現しない。
6. 仮確率が同じ条件では、出場者変更は打順枠の逐球結果・得点・勝敗・順位を変えないという反例試験を置く。v1の既存固定参照/最終frame全byte一致を保持し、v2の形式が異なるframeと同じbyteだと主張しない。
7. v1/v2それぞれ、記録済みDBのcold read・save/load・同installの実force-stop→同checkpoint→次1球を確認。両形式間のslot load、新規置換、generation/ドラフト解除、読込失敗での保持も試験する。fixture作成と実旧APK更新を区別する。
8. 新形式で実UI/Roomの720試合を完走し、独立した開始入力/記録の期待値と照合する。旧v1の既存回帰も保持し、CI時間が必要ならlegacy/newの隔離jobへ分け、旧assertを削って成功にしない。
9. CIで純Kotlin・VM/保存/故障/競合・lint・APKを検査し、API35の隔離emulatorで編成適用→試合→個人記録、320dp/文字1.5倍、回転/停止/エラーを実操作/PNG確認。配布APKそのもののsource/hash/復旧・入手方法と未検証を報告する。ローカルSDK/GradleやユーザーPC画面/入力を操作しない。

受入れの具体的な少数fixtureと独立期待値は、worker実装前に責任者が固定する。workerは専用領域でcore接続・保存・Androidを実装し、責任者が別にコード/数値/成果物をレビューして必要修正を指示する。PR分割は内部作業として管理し、利用者への完了報告はAPKまでまとめる。

## 承認された範囲と次の作業

**打者12人（出場9＋控え3）の限定試作、試合間だけの打順/入替え、個人IDへ記録、仮確率据置き、新形式と旧v1世界の併存とworker実装〜検証APKまでを採用する。** D061/ADRの正式化・設計レビュー/統合後、そのmainから専用workerへ委任する。責任者が独立レビュー/必要修正/CI/APK確認を行い、継続的な統合許可の範囲で問題のないPRをマージする。投手・能力差・一二軍等の細目は別の設計/承認に残す。
