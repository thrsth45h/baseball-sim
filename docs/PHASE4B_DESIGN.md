## 1. 作るものと進め方

**確定済みの合成プレーを受け、ある半回の塁の占有・アウト・得点を更新する検算用参照実装**を提案する。半回は表または裏の一方。この試作は一つの半回だけを扱い、三アウトで停止する。

入力は普通の四球、打者1人アウトかつ他走者移動なしと確定したプレー、合法なフェンス越え本塁打の3種。確率を決めず、打球から結果を生成せず、既存研究を接続しない。単打を「全員1塁進む」と仮定したり、あらゆる三振や捕球飛球で走者が動かないと決めたりしない。

ゲーム側の新しいPython標準ライブラリ参照とする。Android技術の選定、完全な試合生成、公式個人成績・能力の較正ではない。本人の範囲承認→設計PRマージ→worker実装→責任者の独立レビュー/直接修正→継続許可に基づく統合、の順を守る。

## 2. 理由・代替案・限界

Phase 4aはカウント/限定終端まで完成したが、塁と得点は保持しない。次に半回の状態を検証すると、確率係数を増やさずに押し出し、得点加算、三アウト後の停止を具体化できる。

| 案 | 利点と反論 |
|---|---|
| 四球と走者移動なしアウトだけ | 最小だが、複数走者と打者の一度の得点・塁が空になる処理を検証しにくい |
| 上記と合法本塁打の3種（推奨） | 強制進塁、残塁、1〜4得点を未較正確率なしで点検できる。ただし3種から実際の得点分布は推論できない |
| 単打/二塁打/犠牲フライ/併殺まで追加 | 試合へ近づくが、走者ごとの進塁・時系列・第三アウトの種類が必要。固定進塁で埋めない |
| 全プレーの移動先を外部から受ける汎用器 | 将来性はあるが、合法性の責任と不正な得点の拒否条件が大きくなる。今回は保留 |
| 4aと直ちに連結 | 4aの終端だけでは走者移動や本塁打を確定できない。追加事実が必要なため自動変換を作らない |

占有だけでは選手の同一性・打順・触塁履歴・アピール・自責点を表せない。限定された前提の下で状態計算を検算する利点と引き換えに、これらは未対応と明記する。将来の本体では走者ID等を別設計する必要がある。

## 3. 規則上の根拠と試験上の前提

[2026 Official Baseball Rules](https://mktg.mlbstatic.com/mlb/official-information/2026-official-baseball-rules.pdf)の5.05(b)(1)、5.06(b)(1)/(3)(B)/(4)(A)、5.05(a)(5)、5.08(a)/(b)、5.09(e)を確認した。通常四球の一塁付与と押出し、正規触塁、合法本塁打の得点、三アウトを限定契約の根拠とする。原文/PDFは複製しない。

以下のイベントは、**プレーが完了し必要な裁定も確定した後**の試験入力である。全員が必要な塁を正しく触り、追加進塁・失策・走者アウト・妨害・アピールによる変更はなく、サヨナラ条件でもないと入力側で確定している。これを実装が観測から推定するわけではない。四球は生きた球で追加進塁等が起き得るため、単に四球という途中情報だけでこの入力を作ってはいけない。

Xの走者据置きは野球全体の規則ではなく、今回受ける確定プレーの条件。Hも単に「フェンスを越えた」だけでは足りず、正規の本塁打と全得点が確定した条件に限る。バウンドして場外へ出た打球等をHへ補完しない。第三アウトと得点が同じプレーにある場合は時系列とアウトの種類が必要なため、今回の3種へ丸めず拒否する。

## 4. 状態と3イベント

不変な`HalfInningState(outs, bases, runs)`を用いる。

- `outs`: 厳密なint、0〜3。bool/小数/文字列は拒否。
- `bases`: 厳密な3要素tuple、順番は**一塁・二塁・三塁**。各要素は厳密なbool。0/1の整数、余分な要素、可変listをコンストラクタで受けない。
- `runs`: この半回で既に確定した得点の非負int。bool/小数/文字列は拒否し、浮動小数へ変換しない。

JSONはちょうど`outs/bases/runs`の3キーで、basesは3個のJSON booleanの配列。`from_mapping`はこの配列からtupleへ明示変換する。余分/不足キー・重複JSONキー・NaN/Infinity等は拒否。`as_dict`は新しいJSON用値を返す。コンストラクタ/APIの型とJSON表現を混同しない。

この型は**外部で正しく設定した任意の開始局面/途中局面**を受ける。例えば無死二塁からの試験も許し、3種だけで無死走者なしから全状態へ到達できるとは主張しない。過去履歴やrunsと塁の組合せの合法性を復元・証明する検査でもない。outs=3は停止した半回のsnapshotで、basesは最後の残塁を保持する。`half_complete`はouts==3から求め、独立に設定できるstatusは増やさない。イニング番号・表裏・相手得点は保持しない。

| 略号 | 正確なevent文字列 | 確定済み入力の意味と更新 |
|---|---|---|
| W | `walk_forced_only` | 通常四球が完了。打者は一塁、押される走者だけ1塁進む。他の移動/アウトなし |
| X | `batter_out_runners_hold` | 打者だけがアウト、他の走者の最終塁は元の塁、得点/他アウトなしと確定済み。outs+1 |
| H | `legal_over_fence_home_run` | 合法なフェンス越えフェア本塁打と全員の正規触塁が確定。打者+全走者が得点し、塁を空にする。outs不変 |

eventは厳密な文字列のみ。`out/strikeout/flyout/walk/home_run/single`等の曖昧な別名、死球/故意四球/自動判定、単打/二塁打/三塁打、併殺/タッチアップ/盗塁/暴投/捕逸/失策/走者アウト/妨害/アピール/サヨナラは補完せず拒否。文字列に表現されない現実の前提を検査できるとは称さない。

### 更新式と押出しの8通り

一二三塁の占有をa,b,c、得点をrとする。W後は`(true, a or b, c or (a and b))`、得点増分は満塁の時だけ1。Xは塁とrを保ちouts+1。H後は`(false,false,false)`、得点増分`1+占有数`。W/Hはoutsを変えず、Xはrunsを変えない。

下記の数字列は一塁→二塁→三塁の説明用略記で、APIの整数入力ではない。

| W前 | W後 | 得点増分 |
|---|---|---|
| 000 | 100 | 0 |
| 001 | 101 | 0 |
| 010 | 110 | 0 |
| 011 | 111 | 0 |
| 100 | 110 | 0 |
| 101 | 111 | 0 |
| 110 | 111 | 0 |
| 111 | 111 | 1 |

全3種で「プレー前の占有数+打者1人 = プレー後の占有数+得点増分+アウト増分」を満たす。ただし人数保存だけでは誤った移動先を検出できないため、静的72表と個別反例も照合する。

## 5. API、停止、途中処理

`step(state,event)->HalfInningState`は純粋関数。元の状態を変更せず、新しい状態を返す。outs=3への全3イベントは拒否。第三アウト時に塁や得点を消したり、次の半回へ自動遷移したりしない。次の開始局面は呼出し側が明示的に作る。W/Hが続いても便宜的な打席上限でアウトを追加しない。

`replay(start_state,events)`は厳密なlist/tupleだけを受ける。文字列/辞書/iteratorを暗黙展開しない。空列は開始状態を保ち、停止状態にも許す。途中で終端後イベントや不正要素があれば例外とし、元入力を変えず、部分成功結果/traceを公開しない。

返すresult/traceも不変値。各traceは正確な`event/before/after/runs_added`を持ち、`runs_added=after.runs-before.runs`。順序はtuple内の並びで表し、分割処理で振り直す番号は付けない。一括traceと任意の分割位置のprefix trace+残りtraceがそのまま完全一致する。打者/プレーID、永続セーブ形式は別設計。

**Phase 4aのコード・契約・fixture・公開結果は変更しない。4a statusからの自動adapterも今回は作らない。** `strikeout_out/caught_foul_out`だけでは走者据置きを、`walk_awarded`だけでは追加進塁なしを、`fair_play_pending`だけではHを確定できない。4bのW/X/Hはそれぞれ追加事実を含む別契約で、4aや研究の出力を黙って流用しない。新runから4aや研究モデルをimportしない。
