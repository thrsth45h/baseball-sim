# Phase 1d D6 — 既存実データ監査の引き継ぎ

2026-10-28 日本時間。承認済み[Phase 1d設計v1.1](PHASE1D_DESIGN.md)のD6を、既存の実データへ適用するための実行手順。新しいモデル・能力係数・ゲーム仕様を提案または承認する文書ではない。

## 目的と今回の境界

Phase 1dの実装と合成検証は[研究PR #3](https://github.com/thrsth45h/statcast-swing-model-v1/pull/3)で完了した。実ファイルの監査は明示入力がなく未実施だった。次はPhase 1bの取得済みデータについて、出自・年度・座標・列の情報役割と、早期観測の証拠を確認する。

研究コードの確認基準はmain `cba081a13d53684e037738b53a65bdce2abea9a3`。設計正本は[ゲームPR #4](https://github.com/thrsth45h/baseball-sim/pull/4)、設計マージ `cecc3c372ae45c22561b97a59f731f463849f198`。

この工程では既存CLIを使う。新規取得、実データ学習、予測損失の計算、潜在r/aの推定、能力換算、ゲーム統合は行わない。監査に不足する仕様があれば設計側へ戻し、黙って新方式を加えない。

## 明示する入力と選び方

Phase 1bの作業領域にある `data/full/raw/<year>/manifest.json`、`data/full/processed/<year>/metadata.json`、それらに対応する2023・2024・2025年のファイルを使う。実際の作業領域の絶対パスは実装担当が確認し、使ったパスをローカル実行記録へ残す。別チャットのフォルダにキャッシュが引き継がれたとは仮定しない。

1. 各年度の処理済み `pitches.parquet` を対象にする。SHA-256をmetadataおよび提出済み `reports/phase1b/study/data_metadata_<year>.json` と照合する。
2. 各年度のraw取得manifestに登録された非空chunkを、対象期間開始日・終了日・登録名の昇順で最初の1個選び、対応するファイルも対象にする。非空かはParquetの行数metadataで確認し、結果や欠損率を見て選び直さない。manifestのSHA-256と現物を照合する。
3. raw manifestにある登録chunk数と監査したchunk数を分ける。この3つのrawサンプルを全年度・全chunkの品質監査とは呼ばない。登録列情報があれば、manifest上の記述と実ファイルで確認した範囲も区別する。
4. 原データと処理済みデータの列の違いを確認する。`season_data.read_projected` は必要列を選択するため、処理済みデータの列欠落だけを原データの情報欠如の証拠にしない。

元ファイル・manifest・metadataは読み取り専用とする。来歴のない別ファイルを同じデータとして代用しない。見つからない入力やハッシュ不一致は具体的に報告し、その入力を使う監査を中止する。新規ダウンロードや合成データへの置換は行わない。

## 監査の実行

元データの来歴と公式仕様を確認して、各明示ファイル用に最小の監査用来歴JSONを新しい作業出力へ作る。`source_kind`、`years`、`coordinate_schema` を根拠に基づき記す。未知の値を推定でrealや確認済みへ昇格させない。来歴を整形したことは新たに出自を証明したことにはならない。

CLIはファイルごとに新しい出力先を指定する。

```text
python -m baseball_calibration.phase1d audit-input --input <explicit-file> --provenance <explicit-provenance.json> --output <new-directory>
```

まずヘッダ／スキーマ監査を行う。同じファイルの値の標本監査は別の新規出力先で `--inspect-values` を明示して行う。既存CLIが選ぶ列の先頭最大10,000行だけを使い、年度・欠損数を確認する。rawとprocessedで別々に最大10,000行であり、全母集団の推定値とは呼ばない。

年度・座標に関して来歴と値の標本が矛盾した場合は、その矛盾を報告し、後続比較へ渡さない。CLIの成功だけで入力の同一性・全件の年度整合性を証明したとは扱わない。

[Statcast公式CSV仕様](https://baseballsavant.mlb.com/csv-docs)を参照し、2023〜2025年と2026年以降の位置・ゾーン契約を分ける。軌道係数は50ftで定義された値だが、定義地点から推定に使用した観測時間区間までは証明できない。係数から再構成した値を、判断期限以前に得た真正な早期観測と認定しない。

## 成果物と判定

新しい作業ブランチから、研究側へ**監査結果と文書中心のPR**を作る。既存 `reports/phase1d/input-audit` の未実施記録を上書きせず、たとえば `reports/phase1d/real-input-audit/` に小さな集計・ハッシュ・根拠・比較契約を追加する。

提出内容は次を満たすこと。

- 年度別・raw/processed別の入力識別、取得／処理manifestとの対応、実ファイルのハッシュ、監査範囲と未確認範囲。
- 投球前文脈、事後条件、結果ラベル、軌道係数、真正な早期観測候補を区別した表。係数の有無と知覚の観測の有無を別判定にする。
- 判断時点までの観測窓が立証できない場合は `not_verified` を維持する。`no_independent_early_observation` は今回の入力に対する監査結論で、別データ一般の不存在を意味しない。
- 将来の「同じ最終位置等を条件にした行動予測」と「同じ真正な早期情報だけを使う比較」を分け、それぞれの準備状況と不足物を示す。前者だけで心理的機構が識別できるとは主張しない。
- 2025は既閲覧、M1は比較基準、M2 dは能力の正解ではないこと、実データによる較正・認知妥当性・製品採用は未検証であること。
- 生投球行・選手別値・個人フォルダの絶対パス・秘密をGitへ入れない。ローカルのパスと公開レポートの安全な入力名を対応させる。

ハッシュが一致しない場合や入力がない場合も、未実施箇所・必要な入力を正確に記す。これを「実データ監査完了」として処理しない。独立観測が確認できないという監査完了と、そもそもファイルを読めていない状態は区別する。

モデル実装を変える必要はない。コード変更が必要になったら理由・追加仕様を設計側へ戻す。監査結果PRはこの設計・レビュー担当が点検し、問題がなければ継続許可に基づいてマージする。
