2026-11-17。**主な設計基準の採用はD059 CONFIRMED。以下の実装段階・細目は提案であり、今回の変更は文書のみ。** 現在のゲーム側main `9e0f4b513d935af2479fd500967f2cb884858551`（性能改善PR #46統合済み）を実装状況の基準にする。[ADR-0017](adr/0017-pennant-spirits-baseline.md)・[長期方針](LONG_TERM_POLICY.md)も参照。

## 承認された完成像

本人がPC版Pennant Spiritsをベースにしたいと述べ、公式マニュアル21ページを提示した。責任者は「日程を進めながら球団管理、一二軍/打順/ローテーション/起用、選手の成績/成長/移籍歴、ドラフト/契約/補強から翌年へ」という土台と、既定の能力1〜20・内部1球・無期限ペナント・手動/CPU切替を重ねる整理を提示し、本人が「はい」と回答した。

完成像は **球団を確認する → 編成・起用を決める → 観戦または日程スキップ → 成績を振り返る → オフに育成・補強・契約を考える → 次のシーズン**。この一巡を同一セーブで継続して遊べることを開発の軸にする。今の単年度APKや、年度番号だけを増やす処理を、その完成と扱わない。

Pennant Spiritsを機能構成・遊び方の主基準に置き、FM/OOTP等は既定方針に沿う個別機能の追加参考とする。マニュアルの全細目を一括採用したり、下記の実装順序まで本人が個別承認したという記録にはしない。

## 遊べる版へ向けた優先順（提案）

これは製品単位の目標で、各工程の詳細実装を一括承認したものではない。基盤の細分化を目的化せず、必要な内部PRは責任者が管理して一つの利用者向け目標へまとめる。

| 段階 | 利用者が確認できる成果 | 主要な前提・判断 |
|---|---|---|
| A 球団運営の入口 | 球団ホーム、選手一覧/詳細、日程/成績/観戦への往復 | 既存データと実装済み操作をまず結ぶ。未実装画面の空ボタンを増やすことを目標にしない |
| B 編成してシーズンを遊ぶ | 一二軍、控え、打順/投手配置、試合中の交代、手動とCPU委任が進行へ反映 | 登録/位置/投手・守備・走塁/公式記録/能力の効果等の設計が必要。現在の全員同じtoy確率を戦力差の実証としない |
| C 年度をまたいで追う | 年度別/通算の選手・球団記録を残して次のシーズンへ | 年度/選手ID、長期DB/移行、年次処理/再開、世代交代の設計を進める。年度番号変更だけで完成としない |
| D 球団運営を一巡する | 新人獲得、契約/補強、育成/引退/入団、他球団の動きが次の戦力へつながる | D030等の規約・経済/成長モデルとCPU判断を定義する。詳細スタッフAI/高度な編集等は別の段階で追加 |

最初の「球団運営を一巡して遊べる版」の完成条件はA〜Dを通して評価する。Aだけを完成ゲームと呼ばず、複数段階を一度に無制限に実装する指示とも扱わない。能力・公式記録・世代交代・保存の契約は画面作成と並行して設計し、見た目だけで編成や経営が機能したと判定しない。

### 次に具体化する実装候補：A（未承認）

具体案は[球団ホーム・選手一覧/詳細](CLUB_HOME_DESIGN.md)・ADR-0018/D060 PROVISIONALに整理した。以下の目的を画面/データ/世代境界/検証へ落とした提案であり、実装開始の承認を追加したものではない。

球団ホームと選手一覧/詳細を既存の単年度ペナントへ接続する案を、次の設計PRで具体化する。まずID/所属/打順/既存5件数を使い、年齢・能力・守備位置・正式打率等を架空の値で埋めない。既存のseed、日程、試合への3進行操作、結果と保存/復旧を保ち、一覧/詳細を開いて戻ること自体で試合や乱数を進めない。

画面/ナビゲーション、選手の選択保持、長い一覧、再起動/回転、既存セーブへの影響、受入操作列を整理する。詳細な採用判断後に、承認済み設計をworkerへ委任し、責任者が独立レビューする。今回のD059だけを、この未提示の画面仕様や新たな選手/編成モデルの承認に置き換えない。
