# 翌年への移行と年度別成績の試作

- 状態：承認済みの限定試作。D063 CONFIRMED、[ADR-0021](adr/0021-season-history.md)。2026-11-22、[設計PR #55](https://github.com/thrsth45h/baseball-sim/pull/55)の範囲とAPK公開までの進行を提示し、本人が「はい」と回答した。
- 基準：打者タイプ版 [PR #53](https://github.com/thrsth45h/baseball-sim/pull/53) を統合した `0c63966` と、配布運用 [PR #54](https://github.com/thrsth45h/baseball-sim/pull/54) を統合した `4a41104`。

## プレイヤーができるようになること

今は720試合を終えると、そのセーブでできるシーズン進行が終わる。次の試作では、完走後の球団ホームから「翌年へ進む」を明示的に選び、同じ球団・選手・打順のまま翌年を始める。日程スキップは当年の完走で停止する。過去年の順位と選手ごとの既存5件数を閲覧でき、控えで出場がなかった選手も0件として確認できる。履歴の閲覧で操作球団や進行中の試合は変わらない。

現行のv3セーブは途中の試合もそのまま続け、720試合を終えてから翌年へ進める。新規開始も1年目は同じv3の挙動とする。旧v1/v2は従来の単年度として続行・保存・復旧できる。画面の年度は「1年目」「2年目」とし、実暦は付けない。今ある120試合/球団の日程、試合ルール、打者タイプと仮確率を使う。選手の年齢・成長・引退・補強・契約・資金は今回の試作に含めない。公式打率や通算成績の新設も含めない。

## 年度が切り替わるときの約束

- 720試合が確定し、進行中の試合がないときだけ実行できる。確認画面で年度と操作を示す。押下時の保存状態が変わっていた場合は拒否する。確認待ち・失敗・二重入力・復旧で年度や履歴を重複させない。
- 確定した年の12球団の順位と勝敗・得失点、144人の所属と既存の打者イベント件数を、その年の保存済み試合から確定する。所属と人物は不変のIDで記録する。順位は同率同順位など既存計算を保持する。集計は成績画面と同じ値を照合する。過去年の個別試合再生は対象外で、当年の試合結果・直近試合の再生は旧仕様を使う。
- 翌年は当年の結果と集計を空にし、同じ人物ID・タイプ・各球団の打順・操作球団を引き継ぐ。既存の日程内の番号は再利用するので、年をまたぐ識別には世界と年度を含める。年度は正の `Long` を使い、加算は桁あふれを検査する。固定の終了年を設けない。
- 同じ初期seedと年数から同じ試合seedを割り当てる。提案方式は `season-year-seeds-v1` とし、1年目は初期seedそのまま、年 `n` の割当て開始状態は `root + 0x9E3779B97F4A7C15 * 720 * (n - 1)` を 64-bit 符号なしで計算する。既存割当てが1試合につき `Sm64.nextRaw()` を1回呼ぶため、翌年は割当て列の次の720出力から始まる。試合中の乱数や仮確率に変更を加えない。有限の乱数周期の範囲での試作仕様とする。

## 保存の提案と反証

現行の `working_state` と `manual_slot` はそれぞれ当年のチェックポイントを1行に保存する。v3全720試合の実測は1,838,493バイトで、PR #53の中間版はAndroidの行読取上限で696試合時に止まった。このため過年度を連結して同じ行に置く方式は採らない。現行の当年データの形式を使い続け、Roomの追加テーブルで履歴と年度の参照を管理する。

- 完了年は変更不可の単位にまとめ、世界・年度・親履歴を識別できるようにする。保存するのは年度メタデータと球団12行・選手144行の集計。正式な履歴を読み出すときは、選択中のセーブが指す親履歴列だけを参照する。別セーブ分岐の同年度を混ぜない。
- 作業中の状態と手動スロットの保存行に、年次の形式を示す印、初期seed、年度、直前の履歴IDを追加する。版0は既存保存として扱い、v3なら1年目とする。年次の版が立っている行では、参照先が同じ世界の直前年であることと集計の整合性を検証する。メタデータの一部が欠けている場合や過年度参照が破損している場合は読み込みを止め、保存を保持する。旧v1/v2に年度移行を追加しない。
- 年度移行は1トランザクションで履歴の追加、当年を新世代の空状態へ切替、当年の結果行の退役、操作記録の確定まで行う。既存の保存トークン・操作IDで古い操作や再送を判別し、コミット後の状態だけを画面に渡す。年度更新中は既存の進行・セーブ操作と競合させない。
- 手動セーブは試合外に限り、履歴の参照も確定する。ロードは当時の年度・成績・親履歴へ戻り、以後の再進行は新しい分岐とする。例えば1年目途中を保存して2年目へ進んだ後、その1年目から打順を変えて再度2年目へ進んでも、履歴画面で表示するのは再進行した方の1年目。旧履歴行の回収や長期運用の容量保証は別途検討する。同じ年度データと同じ親での再進行は既存の履歴を使い回せる。
- Roomの非破壊マイグレーションを用い、現行のチェックポイントの内容は書き換えない。通常の逐球進行では過年度の全行を読み込まず、履歴一覧と年度詳細の要求時に取得する。旧APKへのダウングレードと長期保存の製品仕様は別判断とする。

## 受け入れ条件

1. 正常なv3の720試合完了時だけ翌年へ進める。確認画面での取り消し、古い画面からの操作、連打、保存失敗、アプリ強制終了で中途半端な年や重複記録を作らない。失敗前後の故障注入と実プロセス再起動で照合する。
2. 年度初日の成績が0件で、144人のID・タイプ、12球団の打順、操作球団が引き継がれる。既存の1年目seed一覧と、事前に別実装で生成した2年目・3年目の各720 seedを照合する。1球・1打席・スキップ・途中復旧は同じ編成と入力なら同じ結果になる。
3. 実データ構造を使う独立集計で、完走年の12球団・144人の成績を全件照合する。手動セーブから年度を戻して異なる打順で進める分岐試験、別世界のロード試験を行う。履歴閲覧だけでは保存や進行を変更しない。
4. 現行Roomの独立fixtureでv1/v2/v3の読取と手動スロット・試合中復旧を確認する。旧形式の乱数・集計・チェックポイントは回帰照合する。新しい履歴表を作っても保存行を消さない。100年分の合成履歴で数値範囲・当年の行サイズ・年度指定クエリを点検する。実機耐久試験とは区別する。
5. CIの隔離Androidで、完走済みの1年目から次年度開始、実際の2年目720試合の進行、3年目開始、2年分の閲覧、手動セーブ・ロードを通す。強制終了後の復旧を検証したAPKを配布対象とし、独立レビュー・実装PR統合後に [GitHub Releases](APK_RELEASES.md) へ添付する。
