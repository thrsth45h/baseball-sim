# Phase 5a: 最小ペナントの設計案

2026-11-01 日本時間。**Proposed / 詳細未承認・未実装**。ユーザーの「次へ」は、Android完成後の設計を進める指示として記録する。本書の試合数・順位規則・保存方式やworker実装開始の承認には代用しない。[決定台帳](../DECISIONS.md)のD057/D058、[ADR-0015](adr/0015-pennant-basic.md)、[長期方針](LONG_TERM_POLICY.md)を参照。

## 1. 今回の到達点と現状

推奨する到達点は、**Androidで12球団の1シーズンを、試合を開いて進めても日程を飛ばしても同じ結果で完走し、順位と限定イベント記録を保存できること**。セーブ・強制終了からの復旧も同じ到達点に含める。経営機能や実力差を作る段階とは区別する。

[Android実装PR #40](https://github.com/thrsth45h/baseball-sim/pull/40)はmain `470467a27d6390b6415e5b16b44c0c1a0aa1704f`へマージ済み。純Kotlin coreに1球入口・9回引分・サヨナラ・固定仮確率・打順別EventCountsがある。一方、球団/選手の永続ID、日程、正式な個人成績、保存・復旧はない。現在のGameSessionにsnapshotだけを渡しても、消費済み乱数やイベント履歴を復元したことにはならない。

新しい純Kotlinのseason層が既存coreを呼び出す。Android依存の保存と画面は外側に置く。旧core/Python/研究コード・既存の固定参照・公開結果は保持する。既存の単独1試合モードも残す。

## 2. 承認を求める仮設定

以下は今回の試作用で、製品版の年間規約や選手編成の永久決定ではない。

| 項目 | 推奨案 |

| 球団 | 2リーグ各6球団、仮ID L1-T01〜06 / L2-T01〜06。名称は仮球団1〜12 |
| 選手 | 各球団固定9打順、計108人。球団IDに結び付けた固定選手IDを持つ。能力・投手・控え・二軍・加齢なし |
| 試合数 | 同リーグ5相手と各24試合、1球団120試合、全体720試合 |
| 主催 | 相手ごとホーム12/ビジター12、球団ごと各60試合 |
| 日程 | 20週。月曜休養、火〜木・金〜日の3連戦。40シリーズ、各試合日に全体6試合。実在年の祝日・球場・移動・雨天を再現しない |
| 対戦範囲 | 交流戦・ポストシーズンなし。リーグ別の順位表を表示 |

120試合を推す理由は、3連戦・相手別/主催別の完全対称を簡単に点検できるため。143試合・交流戦を先に導入する案は、主催数の非対称・年度ごとの調整・追加の順位/日程規約を一緒に決める必要がある。短い30試合だけの案より、1年分の保存量と操作負荷を確認できる。NPBやMLBの公式日程を採用したという主張はしない。

## 3. 日程・試合ID・乱数

同リーグ6球団の5ラウンド総当たりと、ホームを反転した5ラウンドを1組にし、4回繰り返す。1ラウンドは3連戦とする。対戦表の正確な回転順・主催側・第2リーグとの配置は実装前に独立参照表で凍結する。全球団が同日に1試合だけ出場し、連続シリーズも含め相手別24/主催別12の条件を満たすことが契約である。

日程確定後に、`(seasonId, dayIndex, leagueId, seriesRound, matchupIndex, seriesGame)`から安定したGameIdを割り当てる。表示名や現在の配列indexだけをIDにしない。日程の正規順は数値のdayIndex→leagueId→matchupIndexの昇順とし、1〜720のscheduleOrdinalも固定する。日付文字列の辞書順や画面上の並び替えを使わない。仮のseasonIdは第1シーズンとし、日付は週/曜日で表示する。実在の暦年を勝手に採用しない。

試用の`season-seeds-v1`は、正規十進master seedから新しいSm64を作り、確定GameId順にnextRawを1回ずつ呼んで720個の試合seedを**開幕前に割当・保存**する。各試合はそのseedで別のGameSession/ToyPitchSourceを所有する。観戦、UI描画、保存、復旧、並び替えは割当器や別試合の乱数を消費しない。sm64-v1の本番永久固定ではない。年度間の導出規則は次年度移行の別設計で扱う。

初版は同時に1試合だけ計算し、GameIdの確定順で進む。未来の全試合を開幕時に抽選して隠す方法は採らない。開幕時に固定するのは入力定義とseedで、結果は各1球処理から発生する。

## 4. 進行操作

- 日程画面で注目球団を選ぶ。球団選択は画面の注目先で、監督AIや手動采配機能を実装したことにはしない。
- 「次の自球団試合を開く」は、それより前の未消化試合を同じcoreで画面なし進行してから、対象試合を開く。開いた試合では既存の1球/1打席/最後までを使う。
- 「1日進める」「シーズン終了まで」は同じ1球入口を画面なしで反復する。進行中の自球団試合があれば、その同じ試合の続きを進める。別の結果抽選や試合の作り直しはしない。
- 休養日も日程の状態として扱い、架空の試合や結果を生成しない。日の全試合確定後だけ次の日へ移す。
- スキップ中は「停止予約」を受け付け、進行中の1試合を確定してから次の試合の前で止まる。シーズン完了・未完了エラーでも停止する。怪我等の停止イベント/設定は今回まだ存在しない。
- 計算・保存・復旧はUI Thread外。コマンドは1本化し、処理中の進行/ロード/新規開始の連打を受け付けない。画面再生成で追加進行せず、古い処理がロード後の状態を上書きしない。

参加・進行単位・采配担当を同一のenumへ押し込まない（D050）。今回操作できるのは表示と進行であり、采配は未実装。試合を開かない進行でComposeやGamePresentationの生成を毎球強制しない。

## 5. 集計・結果の確定

`Status.COMPLETED`の最終snapshotだけをシーズン結果へ受理する。`GameResult`が作れるだけでは十分でない（既存型はABORTEDもdoneとして含む）。中止・入力不正・投球上限を引分や敗戦へ変換しない。未完了なら日程を止め、GameIdと理由を保持し、勝手なseed変更・再抽選・上限引上げをしない。

各GameIdは未開始/進行中/完了/未完了エラー停止の状態を持つ。完了GameIdの同じ結果の再受理は、集計・日程位置・active状態を含め無変化、異なる結果の再受理はエラー。「同じ結果」はscoreだけでなく、対戦相手/主催/seed/各版/status/outcome/reason、全lineScoreのnull、受理球数、各打順の5countsと選手ID対応、保存する全要約値の値一致で判定する。同scoreでも四球の帰属等が違えば衝突である。scoreにはサヨナラ専用terminalScoreDeltaを含む既存`GameSnapshot.score`を使い、別に足し直さない。

ABORTEDはactive試合に結び付く「未完了エラー停止」として理由・snapshotを永続化する。日程の未消化を残し、完走扱いにしない。再起動後も同じエラーを表示し、再進行・再抽選・手動save/loadは認めない。脱出は、未完了の診断要約と既存の手動slotを保持したうえで、確認付きの「新しい検証シーズンを開始」に限る。これは試合中ロードを許す抜け道や、未完了試合に別seedを割当てる処理とは区別する。

リーグ表は試合数・勝・敗・分・得点・失点・勝率・順位まで。勝率比較は丸め前の整数比で行う。表示丸めで順位を変えず、整数加算/比較のoverflowも黙認しない。勝敗・記録の正本はGameId別の完了結果で、表示用集計はそこから再生成可能にする。

各球団の固定9人に、既存`batterCounts`をその試合のaway/home対応で割り当てる。保存・表示するのは **完了打席イベント数、セーフ安打イベント数（本塁打を含む）、四球イベント数、三振イベント数、本塁打イベント数**。out_holdの件数は他項目からの検算に使える。正式AB/打率/出塁率/RBI/得点/防御率/投手勝敗/Savant指標は補完しない。打順を実在の能力や正式なロスター仕様と解釈しない。

全12球団108人の今回の年度別イベント記録とGameId別の結果要約は残す。過去試合の全投球ログは保存せず、進行中のログだけseed再生で復元する。次年度以降の履歴削除/上書きを認める決定ではない。D054の一二軍・引退後の全選手年度記録は将来の対象として維持する。

## 6. 保存と復旧の提案（D058、未採用）

### 6.1 保存方式と代替案

**今回の試作は端末内SQLiteをRoom経由で使う案を推奨**。core/seasonはRoomに依存せず、外側のSeasonStoreがトランザクション・世代/リビジョン比較を担当する。互換性を確認したRoom/KSP/serializationの版とschemaを、実装前に固定・記録する。最新版への既存toolchain全体の更新は前提にしない。互換導入できなければ黙って技術構成を変えず設計へ戻す。

RoomはSQLiteの抽象化、SQLのコンパイル時検査やmigration支援を提供する。[Android公式資料](https://developer.android.com/training/data-storage/room)を根拠とするが、本作の復旧の正しさを証明するものではない。[Transactionの契約](https://developer.android.com/reference/androidx/room/Transaction)を踏まえ、複数の更新を一緒に確定する。採用する版のAPIは実装時に一次資料で照合する。

小さな単一JSONを原子的置換する案は導入が軽い一方、結果台帳・世代・手動slotを一緒に管理し、今後履歴を検索する拡張で別の仕組みが必要になる。保存を後回しにする案は、次のAPKでも強制終了でシーズンが失われ、試合引き直し防止を後付けするため推奨しない。初回から全長期記録/DB製品設計を完成させる案も範囲が大きい。**Roomの採用は今回用の案で、製品DB/長年のschema互換を自動確定しない**。

### 6.2 自動保存と公開の順序

初回は1つの進行データと、試合外用の手動slotを1つ持つ。同じDB内の論理snapshotをslotとして保存し、使用中のDB本体ファイルをコピーしない（[SQLite WAL](https://www.sqlite.org/wal.html)では関連ファイルも状態を持つ）。保存にはschema/rules/toy/RNG/seed導出版、master seed、日程と試合seed、球団/選手対応、完了結果、集計、現在位置、active試合、世代ID/revisionを含める。

1. 試合を始める前に、GameId・seed・版・初期値・advance呼出し数0のactive recordを永続化する。保存できなければ投球しない。
2. 各操作は候補状態を計算し、保存成功後だけ新状態・ログを画面へ公開する。「1打席」「最後まで」は操作途中の未保存結果を確定表示しない。
3. 進行中checkpointには`advanceOnePitch`の**呼出し数**、受理球数、status/reason/outcome/lineScoreのnull/terminalScoreDeltaを含む全snapshotの値、maxPitches、乱数state/raw/draw/rejection数とsource消費数を保存する。受理球数だけだと、0球受理で停止する処理を区別できない。
4. 試合完了時は、完了結果の一度だけの登録・集計更新・active解除・日程位置/revision更新を**同一トランザクション**で確定する。完了直前のcheckpointを経由する場合も、未集計の完了と二重集計の両方を防ぐ。
5. 途中で保存に失敗したら未保存状態を公開せず停止する。計算済みのmutable GameSessionを破棄し、再試行は最後の永続状態から再構築する。既に進んだメモリ状態へ同じ操作をもう一度足さない。

各更新にはoperationIdを付け、現在の世代ID/revisionをDB更新の比較条件にもする。commit直後の中断等で成否が不明ならDBを再読し、operationId/revisionで確定を判別してから復旧する。画面への旧世代の公開防止だけで保存を保護したことにしない。進行データ内の結果には`(worldId, generationId, seasonId, GameId)`の一意制約を設ける。手動ロードはslotの論理状態を別世代へ復元し、その世代を現在としてatomicに切り替える。旧世代の未来の結果を新世代へ混入させず、古い非同期更新も拒否する。同一GameIdの同値/衝突判定は現在の世代内で行う。CPU計算・試合の再生はtransactionの外で行い、transaction内は短い整合した保存処理に限る。

画面なしスキップは、1試合完了ごとに保存して進捗を公開する。各球の途中結果を画面へ公開/確定する処理ではない。試合中に強制終了しても同じseedから同じ試合の同じ結果になる。ストレージ不足・書込失敗・復旧不整合時に、自動で新規データへ置き換えたり無言で過去へ戻したりしない。

### 6.3 再起動・手動save/load

進行中のactive recordがあれば保存した版/seed/固定定義で新しいGameSessionを作り、保存済みadvance呼出し数だけ内部で再実行する。全snapshot/RNG/source消費数を値で照合し、一致した場合だけ操作可能にする。参照同一性やtoStringの比較で済ませない。再生途中の状態は表示/再集計せず、復旧の再生を新しい試合結果の登録と扱わない。サヨナラ/完了直後も検査する。既に保存された未完了エラー停止は、§5のとおり保存理由/snapshotを表示して止め、再生して続きを許可しない。0球受理abortも呼出し境界を含む診断状態を保持する。

将来、采配・可変選手・外部入力が入るとseedだけの再生では足りない。今回の復旧は固定ToyPitchSource・固定入力定義に限定し、将来へ一般化したと称さない。実行環境由来の非決定的source_errorもseedだけで再現できる保証はなく、不一致ならデータを保持して停止する。版が不明/不一致なら勝手に最新版で再生しない。既存データを保持して読込みを止め、復旧案を別途示す。[migration](https://developer.android.com/training/data-storage/room/migrating-db-versions)でも破壊的fallbackは使わない。

試合外の手動save/loadは認める。保存slotへの論理コピー、ロードによる世代更新と状態切替もatomicにする。active試合があれば手動save/loadを無効にし、アプリを閉じてもactiveの有無は変えない。新しいシーズンで既存進行データを置き換える場合は、別途画面で確認し、無言で消さない。外部DB編集・改造・OSバックアップ差替えに対する完全な不正防止は保証しない。Androidの[Auto Backup](https://developer.android.com/identity/data/autobackup)等とアプリ独自復旧も区別し、試作DBをクラウド/端末間バックアップの対象から除外するアプリ側設定を明記・検査する。端末メーカー等の外部復元まで防止したとは称さない。

保証する受入れ対象は、アプリのプロセス強制終了後に、永続化済みの確定状態から同じ続きを復旧すること。突然の電源断/媒体故障に対する永続性は別の試験であり、この成功で保証しない。実際のjournal/[synchronous設定](https://www.sqlite.org/pragma.html#pragma_synchronous)を検証報告に残す。

## 7. 実装順と検証ゲート

この設計案の承認後に設計PRを統合して、workerへ3つの実装PRに分けて直接委任する案。PRごとに責任者が独立レビュー・修正確認・CIを確認する。同じ承認範囲の通常判断を毎回ユーザーへ戻さない。1と2だけで「Androidペナント完成」と報告せず、3のAPKまでを今回の到達点とする。

| 順番 | 作業 | 必須の検証 |
|---|---|---|
| 1 | 純Kotlinの球団/日程/seed/進行/結果受理/年度イベント集計 | 720試合/120試合ずつ/主催/同日重複/対戦数、固定表の独立照合、観戦3操作/全skip/混在/別注目球団でGameId別全結果一致、完了/未完了/重複/衝突、サヨナラ、丸め前順位 |
| 2 | Room保存・復旧・手動slot、世代/revision | commit前/中/後、試合開始/1球/1打席/最終球/サヨナラ/集計直前直後の障害注入、0球受理abort、重複callback、ロード後の旧世代、保存失敗、未知schema/版、再起動後の全結果一致 |
| 3 | Composeの日程/順位/限定記録/試合への接続・debug APK | 全skip720試合完走、観戦とskipの混在、停止予約、画面再生成、連打、同一データの再起動、試合中手動save/load禁止、保存エラー表示、隔離CIエミュレータで操作 |

旧coreの7件・既存appとPythonの回帰を残す。凍結の単独試合seed例も不変とし、日程層のseed割当と取り違えない。実装コードを見る前に別担当が日程表・割当seed・小さな結果台帳/集計の期待値を凍結し、worker実装の答え合わせだけに依存しない。

最低3つのmaster seedで全720試合を実行し、全skipと混在進行の数値/結果が一致することを検査する。実行時間・最大メモリ・保存容量・保存/復旧時間を記録する。現段階で未実測の「高速」や秒数を合格済みと主張しない。720試合の全投球ログを同時保持せず、試合要約と年度集計を保持する。

APKのsource/実hash/取得期限、検証済みOS・未検証事項を報告する。CIビルドとエミュレータ/実機検証を区別し、ユーザーPC画面/入力/既存環境を操作しない。SDK等のローカル導入を前提にしない。

## 8. 今回採らないものと判断の境界

実在日程、交流戦/優勝決定戦、延長、雨天/移動、本格CPU采配、投手ローテ、編成/二軍、怪我、成長/退団/世代交代、契約/財政、能力較正、Statcast統合、公式個人成績、次年度移行/歴史検索、1000年耐久完了、製品セーブ互換/配布署名は対象外。D029/D030/D031の製品規約、D056の長期保存設計はOPENのまま。二軍を一軍と異なる簡略試合方式へ変更する決定もしない。

承認を求めるのは、(a)120試合・交流戦なし等の試作用条件、(b)限定イベント集計の範囲、(c)Roomを用いた試合外save/loadと試合中の自動復旧、(d)3PRでAndroid APKまで仕上げる実装開始。承認までは文書のレビュー/修正だけを進め、実装委任・設計PRマージはしない。DB導入や復旧が想定以上に難しくても、無保存版を黙って完成扱いにせず、根拠と縮小案を示す。
