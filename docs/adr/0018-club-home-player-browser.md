# ADR-0018: 球団ホームと選手一覧/詳細を既存ペナントへ接続する案

- Status: **Proposed**（2026-11-17）
- 関連決定: D060 PROVISIONAL、D059 CONFIRMED。D029/D030/D031/D056 OPEN。
- 正本: [球団ホーム設計案](../CLUB_HOME_DESIGN.md)
- 本人の指示: D059の完成像に「はい」、次の具体設計の案内に「続けて」。今回具体化した画面/復元/初期モード等の詳細・実装開始は未承認。

## 現状と問題

main `edc803ed16a57339e4b87330ae0c83fe86900756`で、日程/試合/順位/限定件数/保存は単一のペナント画面にある。固定108人のID/所属/打順/5件数を公開値から参照できるが、選手一覧から個人詳細へ移動できない。操作球団の保存変更と、情報を見る球団の切替を混同すると、閲覧だけで将来の進行対象を変えてしまう。

## 候補と提案理由

- A（推奨）: 既存データだけで球団ホーム/選手一覧/詳細を作り、日程/順位/記録/試合/設定へ接続。閲覧状態とworld/generationを結び付け、進行/保存とは独立にする。
- B: 単一画面へ個人詳細だけ追加。変更は小さいが、球団運営の入口と情報の行き来が整理されない。
- C: 能力/プロフィール/編成/経営も同時実装。見た目は豊かになるが、新しい規約/モデル/保存契約を未承認のまま混ぜることになる。

Aは既存の確定値と検証を使い、利用者が見て操作できる進歩を出せる。ただし戦力差や編成の面白さを検証するものではなく、これだけで球団経営完成とはしない。

## 影響と反例

新規起動の既定モードをペナントにする案と、既存の1試合への切替保持を明記。UI状態の復元にはseed/選手IDだけでは足りず、world/generationの検証が必要。revision更新で画面を閉じず、同seedのload/新規で古い選択を採用しない。

閲覧だけでActions/read/reloadや再生を呼ぶ、他球団を見るためにSELECTを呼ぶ、ページ破棄でbulk処理を作り直す、完了callbackで古い画面へ移動する実装は不合格。公開UI値から投影し、エラー/停止予約を共通表示する。通常起動時の既存の保存復旧は維持する。

確認ダイアログのtoken比較は表示時とcommand受付時の公開済みstateを対象とする。UIへ未公開の外部DB変更まで確認が拒否するという保証や、新しいexpectedToken付きcommandは追加しない。既存の保存競合制御と、このUI上の古い確認の破棄を区別する。

## 確認と採否

正本の全108人/5件数、fake Actions追加呼出し0、実DBの閲覧前後全byte不変、世代変更、回転/bulk/停止、既存セーブ/全720/force-stopの検査を実装後の条件とする。これはまだ実行済みの記録ではない。runtime/研究/セーブ/CIは設計PRでは変更しない。

本人への範囲提示後に採用を記録し、設計統合→worker実装/CI→責任者独立レビュー/修正→問題のないPR統合/APK報告とする。現段階のProposedを承認済みや実装済みと扱わない。
