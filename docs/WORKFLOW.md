# 設計変更・実装・レビューのGitHub運用

## 目的と役割

GitHubの `main`、Issue、PR、`DECISIONS.md` を**責任者とworkerの共通情報源**とする。ユーザーは責任者と相談し、重要な設計判断・仕様変更を承認する。責任者がworkerサブエージェントを直接管理するため、ユーザーによるエージェント間の仲介は不要。

| 役割 | 作業 |
|---|---|
| 責任者（設計・相談・レビュー・進行管理） | 設計Issue/ADR/設計PR、代替案・根拠・反証、仕様相談と承認記録、workerへの直接割当、コードレビュー・修正指示・統合・引き継ぎ |
| workerサブエージェント（実装・テスト） | **マージ済み・承認済み設計**を参照し、指定された専用作業領域・ブランチで実装・テスト・修正。結果と追加判断事項を責任者へ返す |
| ユーザー | 設計の採否、保留範囲、設計PR・実装PRのマージ許可 |

## フロー

1. **提案**：新機能・仕様変更はIssueに背景、決定ID、候補案、未解決事項、検証条件を記録する。小規模な仕様提案ではIssueを省略して設計PRから始めてもよい。
2. **設計PR**：`design/<topic>` ブランチで `docs/adr/0000-template.md` を使い、設計書・必要な `DECISIONS.md` の **OPEN/PROVISIONAL** を更新する。設計PRは原則ドキュメントだけとする。
3. **検証・議論**：責任者が自説にも反証を行い、実装難度・既存コードとの競合を確認。根拠、期待される効果、代替案、統計上の限界、受け入れテストをPRに明記する。
4. **明示承認**：責任者が採用内容・対象範囲をユーザーに示し、ユーザーが明示承認する。本人のPRコメントまたはチャットで得た承認内容・範囲を設計PRに記録する。**Codexがユーザーの承認を代行しない。** CI・技術レビューや研究方向への賛成だけを、未提示の詳細仕様の承認と扱わない。
5. **正式化**：承認済みの決定だけ `CONFIRMED` にして、根拠と承認PRを残す。未承認は `OPEN/PROVISIONAL`。ユーザーのマージ許可を得て設計PRを `main` へ統合する。
6. **worker割当・実装PR**：責任者が現在のブランチ・HEAD・未保存変更と最新mainを確認し、既存作業を保護する専用worktree等と `impl/<topic>` ブランチを用意する。承認済み設計のcommit/PR、許可した範囲、編集可能な作業領域、必要な検証、禁止事項をworkerへ直接渡す。workerは実装・テストとPRを担当し、追加判断を責任者へ戻す。
7. **責任者の独立レビュー・修正反復**：責任者がworkerの説明だけで合格にせず、コード差分・情報漏洩・統計・テスト・必要な再実行・既存研究との互換を自ら検証する。問題があればworkerへ直接修正を指示し、変更後のheadで再レビューする。仕様変更が必要ならユーザーへ戻す。問題が解消し必要な検証が成功したら、継続的なマージ許可の範囲内で統合する。
8. **引き継ぎ**：責任者が `docs/HANDOFF.md` に現在の有効PR、承認範囲、マージSHA、作業領域、次工程と未解決事項を記録する。ユーザーには結果と次の重要判断を報告し、workerへの転送・取次ぎを求めない。

## 例外・競合・強制の限界

- 誤字、リンク整備、明らかな仕様非変更のリファクタリングは設計Issue/ADRを省略できるが、原則PR・レビューは維持する。
- 1ブランチの書込み担当は1エージェントとする。同じファイルを並行更新する場合は作業領域とPRを分離し、取り込み順を決めてから着手する。責任者はレビュー中のworker領域を同時に編集しない。
- 設計PRが未マージなら、workerは提案を承認済みとして実装しない。
- 研究コードは `statcast-swing-model-v1` が正本。研究結果とゲーム設計は相互にリンクし、製品採用と研究PRのマージを混同しない。
- **この文書・テンプレートは運用ルールであり、GitHubの直接pushや無レビューmergeを技術的に防止しない。** 強制する場合、ユーザーがリポジトリの Settings → Rules → Rulesets（またはBranch protection）で `main` の「PR必須」等を設定する。GitHubプランや個人リポジトリによって利用条件は異なる。
- GitHub上のPRレビュー承認と、**ユーザー本人による仕様採用**は別の意味。ユーザーによる明示的なマージ許可も必要。

設計PR：根拠・代替案・影響・承認範囲・決定台帳・参照先が整理済み。

実装PR：承認済み設計PRと紐付き、テストと独立レビュー、既知の制約・ユーザーのマージ許可が記録済み。
