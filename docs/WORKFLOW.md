# 設計変更・実装・レビューのGitHub運用

## 目的と役割

GitHubの `main`、Issue、PR、`DECISIONS.md` を**2つのCodexチャットの共通情報源**とする。チャット履歴は自動共有されない。

| 役割 | 作業 |
|---|---|
| 設計・レビュー用Codex | 設計Issue/ADR/設計PR、代替案・根拠・反証、実装PRの独立レビュー |
| 開発用Codex | **マージ済み・承認済み設計**を参照する実装ブランチとPR、テスト・修正 |
| ユーザー | 設計の採否、保留範囲、設計PR・実装PRのマージ許可 |

## フロー

1. **提案**：新機能・仕様変更はIssueに背景、決定ID、候補案、未解決事項、検証条件を記録する。小規模な仕様提案ではIssueを省略して設計PRから始めてもよい。
2. **設計PR**：`design/<topic>` ブランチで `docs/adr/0000-template.md` を使い、設計書・必要な `DECISIONS.md` の **OPEN/PROVISIONAL** を更新する。設計PRは原則ドキュメントだけとする。
3. **検証・議論**：設計用Codexが自説にも反証を行い、開発用Codexは実装難度・既存コードとの競合を確認。根拠、期待される効果、代替案、統計上の限界、受け入れテストをPRに明記する。
4. **明示承認**：採用内容・対象範囲をユーザーに示し、ユーザーが明示承認する。承認内容は設計PRに本人がコメントするか、別チャットでの承認内容を転記してユーザーに確認する。**Codexがユーザーの承認を代行しない。** CI・技術レビューは設計承認ではない。
5. **正式化**：承認済みの決定だけ `CONFIRMED` にして、根拠と承認PRを残す。未承認は `OPEN/PROVISIONAL`。ユーザーのマージ許可を得て設計PRを `main` へ統合する。
6. **実装PR**：開発用Codexは最新 `main` から `impl/<topic>` ブランチを作る。設計PR/ADR/決定IDと実装範囲をPRに明示し、テストを実行。仕様の追加決定が必要なら設計PRに戻す。
7. **独立レビュー**：設計側が実装PRを検証（仕様適合、データ漏洩、統計、テスト、性能、セーブ互換など）。実装側が修正し、結果をPRに記録。ユーザーが許可するまでマージしない。
8. **引き継ぎ**：`docs/HANDOFF.md` に現在の有効PR、マージSHA、次工程と未解決事項を更新する。次のCodexチャットは最初にこれらのURLと最新 `main` を読む。

## 例外・競合・強制の限界

- 誤字、リンク整備、明らかな仕様非変更のリファクタリングは設計Issue/ADRを省略できるが、原則PR・レビューは維持する。
- 1ブランチの作業担当は1チャットとする。同じファイルを並行更新する場合はPRを分離し、取り込み順を決めてから着手する。
- 設計PRが未マージなら、実装チャットは提案を承認済みとして使わない。
- 研究コードは `statcast-swing-model-v1` が正本。研究結果とゲーム設計は相互にリンクし、製品採用と研究PRのマージを混同しない。
- **この文書・テンプレートは運用ルールであり、GitHubの直接pushや無レビューmergeを技術的に防止しない。** 強制する場合、ユーザーがリポジトリの Settings → Rules → Rulesets（またはBranch protection）で `main` の「PR必須」等を設定する。GitHubプランや個人リポジトリによって利用条件は異なる。
- GitHub上のPRレビュー承認と、**ユーザー本人による仕様採用**は別の意味。ユーザーによる明示的なマージ許可も必要。

### ユーザーによる継続的なマージ許可（2026-10-28）

ユーザー本人から **「以降問題なかったらマージまでやってください」** と指示を受領した。[研究PR #3のマージ記録](https://github.com/thrsth45h/statcast-swing-model-v1/pull/3)にも記録済み。

この指示が有効な間は、承認済みの作業範囲に合致し、レビューと必要な検証で問題がなければ、都度のマージ確認を求めずマージまで進める。上記のマージ許可要件はこの継続許可で満たされる。対象head・CI・統合先を確認し、結果を記録する。新たな仕様の採否・能力係数・製品採用の承認を代行する指示ではない。ユーザーが停止・取消・範囲変更を指示した場合はそれに従う。

設計PR：根拠・代替案・影響・承認範囲・決定台帳・参照先が整理済み。

実装PR：承認済み設計PRと紐付き、テストと独立レビュー、既知の制約・ユーザーのマージ許可が記録済み。
