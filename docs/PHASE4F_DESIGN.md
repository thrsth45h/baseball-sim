## 1. 今回の完成条件と優先順位

**新しい1コマンドで、仮の2チームが1球ずつ自動進行し、試合終了・スコア表示まで到達すること**を次の目標とする。ルールの小機能ごとに次工程を増やさず、本書の統合試作を一つの実装PRで仕上げる。必要な検証と独立レビューを行う。

Python標準ライブラリのCLIで始める。固定2チーム各9打者、チーム別打順、仮の一球入力生成、旧カウント/塁/得点処理、下記終了条件、イニング別スコア・簡単なイベント件数を一度につなぐ。守備位置別の配置、投手交代や選手能力はまだモデル化しない。選手は合成IDと表示名だけで、全員同一の仮モデルを使う。

この完成条件は「限定条件の自動試合試作」であり、一般の全プレー/公式記録に対応した完成試合エンジンではない。Android画面、12球団日程、球団経営、セーブ/復帰は後続の別設計。D032のAndroid技術・DBやD031の製品リーグ規約を確定しない。

## 3. 1球の入力生成は交換可能なstub

この試作の `ToyPitchSource` は、**判定済みの一球イベントを供給する試験用部品**。BB/K/安打数/最終得点を先に抽選しない。各投球イベントを旧カウントへ反映し、打席/得点と集計はその後に決まる。

最終ゲーム方針D022の投球真値→知覚→判断→接触→打球→守備という上流は、このstubの内側では**未実装**である。上流を実装済み・認知妥当性を検証済みとは称さない。投球真値/潜在能力をスイング判断へ直結する機能を新設せず、選球眼と積極性の効果を入れない。EV/LA/方向を結果の後に捏造せず、今回はEV/LAとSavant指標を出力しない。D022/D023の製品方針は維持する。

固定プロファイル `toy-v1` の**未較正な仮の整数重み**を次に示す。リーグ平均へfitした数値、MLB能力効果、能力1〜20の変換ではない。両チーム・全打者に共通とし、カウントや得点による追加補正も使わない。

| 一球イベント | 重み/100 |
|---|---:|
| called_ball | 35 |
| called_strike_caught | 15 |
| swinging_strike_caught | 15 |
| ordinary_foul_uncaught | 15 |
| fair_ball_handoff | 20 |

fairのときだけ次を条件付きで抽選する。このstubは打球物理のモデルではない。

| 仮のfair結果 | 重み/100 |
|---|---:|
| 打者アウト・走者据置き | 65 |
| safeな進塁候補1塁分 | 22 |
| safeな進塁候補2塁分 | 7 |
| safeな進塁候補3塁分 | 1 |
| 正規触塁済みの合法フェンス越え本塁打 | 5 |

1/2/3塁分の候補では、仮の `ToyAdvancePolicy` が当初塁iの各走者を `min(i+候補値,4)` へ進め、打者は候補値の塁へ置く。この**一定進塁は今回のproviderだけの仮設定**。旧4eで許した据置き等を禁止する一般規則ではない。通常プレーは旧4eへ外部確定済みの行先として渡す。将来の進塁方策はこの部品を交換して生成する。投球/結果のsourceと進塁policyをカウント/試合終了の処理から分ける。

全員safe・正規触塁・失策/追越し/妨害/アピールなし、投球間の盗塁/暴投/走者アウトなしという合成条件を維持する。アウトは打者だけ・走者据置き。併殺・犠飛・死球・失策・盗塁・一般の第三アウト得点は生成しない。

## 4. 打順・1球処理と旧コードの再利用

各チームに9個の一意な合成打者IDと別々の次打者indexを持つ。打席完了後だけindexを1進め、9人で循環させる。半回開始時に1番へ戻さない。Begin/Pitch/結果解決/Advanceは新controllerが明示actionとして旧4eへ渡し、旧APIの契約を変えない。結果待ちだけで打順や打席完了件数を更新しない。

1球の進行関数を共通入口とし、全自動実行も同じ関数の反復にする。必要ならBeginを発行→1球入力を取得/検査→Pitch→必要な解決を1回→打順/件数更新→終了判定→必要ならAdvance、の順序をログで追えるようにする。fair結果はfairの場合だけ取得する。**fair結果まで揃って型/行先等の検査を完了してから、その球のPitchを適用する。** fair結果不足/不正ならその球は未受理（投球数/カウント/完了打席数を増やさない）としabortedへ進む。既に出したBegin等は受理済みログへ残す。停止理由を専用abort markerに保存し、記録入力replayでも理由と部分状態を保持する。不正な任意オブジェクトをそのまま公開JSONへ直列化しない。

許可する旧runtimeは11パス: shared `prototypes/__init__.py` と、4a/b/c/d/eそれぞれの `__init__.py/model.py`。型と旧parser/stepの利用・source identity hashに限る。旧I/O/runner/fixtures/成果物・研究モデルは新runの入力にしない。旧4a–4eのcode/契約/fixture/tests/CI/results/flagsは変更しない。新しい進行/trace/resultの型は4fに置く。

## 5. 終了条件とサヨナラの分離

MLB 2026 [公式規則](https://mktg.mlbstatic.com/mlb/official-information/2026-official-baseball-rules.pdf)5.04(a)、7.01(a)/(e)、9.06(f)/(g)を参照した。通常の9回表終了時ホーム先行、9回裏の勝越し、フェンス越え本塁打の全得点と、終端安打価値の区別を設計の根拠とする。**9回同点で引分・延長なし**はMLB規則から導かれる条件ではなく、今回の試作用の独自設定である。

| 局面 | この試作の処理 |
|---|---|
| 1〜8回の三アウト | 旧Advanceで表裏/次回へ進む |
| 9回表三アウト、home > away | ホーム勝利で終了。9回裏のBegin/Pitch/RNGを実行しない |
| 9回表三アウト、home <= away | 9回裏へ進む |
| 9回裏プレーでhome > awayとなる | サヨナラで終了。非HRは勝越しに必要な得点まで、合法フェンス越えHRは全員分を得点 |
| 9回裏三アウト、away > home | ビジター勝利で終了 |
| 9回裏三アウト、away = home | 試作用引分で終了。10回へ進めず、延長走者も置かない |

旧4e/W/H契約はサヨナラなしの完了プレーを前提とする。**サヨナラ候補を旧Resolve/ResolveSafeHitへ渡してから得点を切り捨てる実装は禁止**。その球のBegin/Pitchは通常どおり旧処理で受理し、結果解決だけを新4fの専用終端処理へ先に分岐する。非終端の通常プレーの結果解決だけを旧stepへ委任する。

終端処理は次のように限定する。

- 四球: 正規触塁済み・強制進塁だけ。満塁時の1得点で勝越す場合だけサヨナラ四球。その他は旧処理。
- safe進塁候補: まず厳密な型/占有対応/逆走/衝突/順序を検査する。候補として本塁到達する当初走者を先行者（三塁→二塁→一塁）の順に扱い、勝越しに必要な人数だけ得点する。打者の一塁到達も外部の合成条件として確定。候補の塁数を公式単打/二塁打/三塁打の価値として確定しない。
- フェンス越えHR: 全走者と打者の正規触塁完了が与件。1+当初占有人数の全得点を反映して終了。

専用終端eventには終了直前snapshot、入力候補、正確な得点増分/先行走者の得点対象、最終scoreを保存する。旧stateは**最後の完全な投影、終端プレー解決直前**を表す。これを終端後の塁配置や消費済みcountとして返さない。終端後の旧sequence snapshotは作らず、新GameResultで完了を表す。最終score/最終half得点は直前snapshot+終端増分から導き、増分を二重加算しない。通常終了は最後の旧snapshotのscoreをそのまま使う。試合完了後は追加投球・解決・Advance・source/RNG呼出しを拒否/停止する。

9.06(f)/(g)に基づく公式安打価値・AB/RBI/2B/3B等の公式記録裁定は今回は行わない。サヨナラの候補2塁分を公式二塁打と表示する等の誤記を避ける。

## 6. 結果表示とログ

結果は `completed` と `aborted` を区別し、正常完了だけ `away_win/home_win/draw` を付ける。得点はプレー増分から導き、最終得点の事前抽選や補正をしない。

- イニング別スコア（1〜9）と合計得点。実行した0点は0、裏省略/未到達はnullとし、表示では`—`。サヨナラで途中終了した最終halfにはその旨を添える。
- チーム別・打者別の**イベント集計**: 完了した打席数、safe到達した打球件数（HRを含む）、四球、三振。HR件数は別欄で可。公式打率/AB/RBI/長打価値/投手勝敗/エラー数/Savant値は生成しない。投球総数と終了理由を表示する。
- 完了打席数と打順、得点/件数は同じ時系列ログから再集計して一致させる。sourceの候補結果や未完了fairから安打等を先に数えない。

新CLI案:

```powershell
python -m prototypes.phase4f run --seed 42 --output data/prototypes/phase4f/game-01
```

seedは厳密な0以上2^64未満の整数。標準プロファイルは固定toy-v1で、外部raw/model/能力入力や自由な重み変更・resumeはCLIに追加しない。`--max-pitches` は正の厳密整数、既定10,000。端末へ短いスコア/終了理由/出力先を表示し、READMEにそのまま動かせるコマンドと試作の限界を記載する。

主要5成果物は `plan.json/events.json/result.json/REPORT.md/SHA256SUMS.json`。planに仮設定・seed・source/policy版・Python/RNG・source identity・終了規約と未採用範囲を記録し、主要5ファイルへ時刻/絶対パスを入れない。新namespace `data/prototypes/phase4f` または `reports/phase4f` の新しい子だけへ出力し、既存出力/旧namespace/入力重複/外部・実junction/symlink迂回を拒否する。

## 7. 乱数・再現性・停止

各試合のsourceが専用の `random.Random(seed)` を所有する。グローバル `random.seed()` やグローバルRNGを使わない。投球eventに `randrange(100)` を1回、fair時だけfair結果へもう1回。表の順に半開累積区間で対応させる。例えば投球draw0〜34はball、35〜49はcalled strike。一定進塁に追加乱数は不要。seed/版と各draw・選択eventをログで結び付ける。

同じPython/source/profile/seed/上限なら実行順や他試合に依存せず主要5成果物がバイト一致する。別言語・将来Python版への乱数互換や製品セーブ互換は今回保証しない。記録した一球入力列を再投入するreplayはRNG不要で、試合終了と集計が生成実行に一致する。自動実行/一球ずつ反復も同じ経路を通す。

投球上限、source不足/不正等は `aborted`（未完了）で、勝者/引分を付けない。強制三振/アウト/得点調整で完走させない。部分scoreは部分値としてだけ表示し、理由・受理済み投球数・ログを保存する。CLIは正常完了0、未完了2、入力/出力先等の利用エラーは非0で終了する。10,000球で十分という野球上の主張はしない。単なる異常停止の仮の安全上限である。

上限は**次球を取得する前**に確認する。上限ちょうどの投球も、その球の結果解決と終了判定まで処理し、そこで試合が終わればcompletedを優先する。まだ続く場合だけabortedとし、次打者Beginや余分なsource/RNG呼出しをしない。
